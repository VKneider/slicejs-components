Form

Overview

Form builds a form from a schema and composes the library's own components (Input, Select, Checkbox, Switch, …). It renders sections, separators, per-field labels/descriptions and validation errors, reads the values back, and validates on submit. It is a plain Visual — drop it in a view or a Modal body.

Schema

Each item is discriminated by kind:

Field item:

  • name — key in the values object.
  • label, description — field chrome rendered by the Form.
  • component — a Slice component name, built via slice.build.
  • props — props passed to that component.
  • valueProp — which prop holds the value (default 'value'; use 'checked' for Checkbox/Switch).
  • value — initial value (merged into props under valueProp).
  • required — true or a custom message.
  • validate(value, values) — returns an error string (falsy when valid). Runs on submit.

Steps

A schema item may be a step, with its own nested schema:

  • Values live in one Form. Every step's controls stay built, so what you typed on step 1 is still there after three Nexts. That is the thing wizards usually get wrong.
  • Next validates the steps behind you, not just the current one, and refuses to move while any of them is invalid — painting the errors in place.
  • Back never validates. Leaving a half-filled step is allowed; only moving on is gated.
  • The progress indicator cannot skip validation. Clicking a step ahead is refused exactly as Next would be, so the indicator is a shortcut and not a hole.
  • The last step's button is the Submit button, and says submitText.
  • A failed Submit cannot strand you. Submit checks every step; if the first problem is on a step you already left, the form goes back to that step and focuses the field instead of printing its message on a hidden one.
  • A schema with no step is one implicit step: no progress bar, no Back, no Next.

stepIndex, stepCount, isStepped, nextStep(), prevStep() and gotoStep(i) are public. nextText sets the label of the advance button.

Groups

A group is a set of fields the user can add as many of as they need — phone numbers, addresses, team members. Without it, no flat schema can express "however many of these do you have?".

  • name is required — without it the items could not be keyed at all.
  • min and max bound the item count; the Remove buttons disappear at min and the Add button hides at max. Omit min and a group starts with one item.
  • value seeds the first item, and reset() restores it.
  • Each item's fields are stored internally as phones[0].number, so setValue('phones[1].number', x) and setError(...) work on them with no special cases.
  • getValues() hands the array back nested — { phones: [{ number, note }] } — which is the shape you declared. Flattening is an implementation detail you never see.
  • Items are added and removed in place; the form is not re-rendered, so nothing typed elsewhere in it moves or is lost.
  • required applies to every item, so an empty second phone blocks submit.

Layout

Three presentation props, and one per-field opt-out.

full: true on a field keeps it out of a shared grid row. Sections and separators always span the full row.

Text fields

Input and Textarea know they are inside a Form and step aside for it:

  • The label is the Form's. The field is set to labelPlacement: 'above' with no label of its own, so the Form's label is the only one. The field takes it as its accessible name, and clicking the label focuses the field.
  • The error is the Form's. The field does not show its own messages (validateOn: 'manual'); the Form prints one message under it, in the same style for every kind of control. The field still draws its own red border, so there is one red edge in the field's own shape.
  • Its rules count. After the schema's required and validate, the Form asks the field for its own verdict, so type: 'email', min, max, minlength or a field validator set in props work without repeating them in the schema.
  • Errors follow the value. A field with an error on screen is checked again as it is edited, so the message goes away as soon as it is fixed instead of waiting for the next Submit.
  • A failed Submit takes you there. Focus moves to the first field with a problem.

Anything you pass in a field's props wins over these defaults.

Language

The built-in texts are slice.form.* keys with English and Spanish defaults, registered by shared/text/texts.js in the translator's lowest layer: an app dictionary always wins, and the component keeps its English text when the translator is off. The text prop texts still wins over the dictionary. Keys: submit, next, back, remove, removeItem, add, item, itemNumber, required, progress, step, stepOf.
